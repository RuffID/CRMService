# AGENTS

Этот файл задает общее правило навигации по проекту через локальные `AGENTS.md`.

## Архитектура проекта

Проект разделен на несколько слоев:
- `CRMService.Web` — веб-интерфейс, Razor Pages, API-контроллеры, фоновые службы хоста, middleware, фильтры и регистрация зависимостей;
- `CRMService.Application` — прикладная логика: сервисы пользователей, отчетов, планов, синхронизации справочников, обработки вебхуков и сущностей Okdesk;
- `CRMService.Contracts` — DTO, модели запросов и единый контракт результата операций;
- `CRMService.Domain` — доменные модели CRM, авторизации, справочников и сущностей Okdesk;
- `CRMService.Infrastructure` — доступ к базам данных, репозитории, UnitOfWork, внешние HTTP-запросы, JWT и сервисные операции инфраструктуры.

Основной пользовательский интерфейс строится вокруг Razor Pages. Страницы обычно отдают статическую разметку и загружают данные через handlers PageModel или отдельные API-эндпоинты. Клиентская логика лежит в `CRMService.Web/wwwroot/js`, а серверная прикладная логика — в сервисах `CRMService.Application/Service`.

Данные из Okdesk и связанных источников попадают в локальную CRM через ручные API-команды, фоновые обновления и вебхуки. Для MainContext использовать узкие сценарные Unit of Work (`IAuthorizationUnitOfWork`, `IPlanSettingsUnitOfWork`, `IReportsUnitOfWork`, `ICompanyDirectoryUnitOfWork`, `IEquipmentUnitOfWork`, `IIssuesUnitOfWork`). Read-only доступ к OkdeskContext разделён на предметные source-контракты. Не смешивать прямой доступ к контекстам с прикладной логикой и не создавать новый глобальный агрегатор repositories.

## Документация функционала

При изменении функционала нужно создавать или обновлять ближайший локальный `AGENTS.md`, если меняется смысл директории, сценарий работы страницы, сервисная зона или важное правило сопровождения.

Локальный `AGENTS.md` должен кратко отвечать на вопросы:
- за что отвечает директория;
- какие ключевые сценарии здесь реализованы;
- где искать связанную клиентскую, серверную или доменную логику;
- какие правила важно сохранить при изменениях.

Если меняется поведение страницы, которое важно для пользователя или менеджера, обновлять также `README.md`.

В директориях с важной функциональностью, отдельными архитектурными зонами или нетривиальными правилами нужно создавать собственные `AGENTS.md`.

Локальные `AGENTS.md` нужны, чтобы:
- помечать назначение директории;
- кратко описывать ключевые особенности функционала;
- фиксировать важные архитектурные ограничения и договоренности;
- подсказывать, где искать связанную логику;
- снижать время на вход в код и навигацию по проекту.

Когда добавлять локальный `AGENTS.md`:
- при появлении новой крупной функциональной области;
- при выделении отдельного слоя, модуля или интеграции;
- когда в директории есть правила, которые неочевидны из кода;
- когда без краткого описания сложно быстро понять границы ответственности.

Что писать в локальном `AGENTS.md`:
- за что отвечает директория;
- какие сущности, сервисы или сценарии в ней сосредоточены;
- важные связи с соседними слоями и модулями;
- ограничения, инварианты и правила внесения изменений;
- ссылки на соседние локальные `AGENTS.md`, если это помогает навигации.

Правила ведения:
- писать кратко и по делу;
- держать описание рядом с кодом, к которому оно относится;
- обновлять `AGENTS.md` при изменении архитектуры или смысла директории;
- не дублировать очевидное из кода без необходимости;
- использовать локальные `AGENTS.md` как карту проекта, а не как место для случайных заметок.

Правила проверки изменений:
- если изменения затрагивают только `.js`, `.cshtml`, `.css` или другие клиентские файлы без правок C#-кода и проектных файлов, не запускать `dotnet build`;
- `dotnet build` запускать только когда это действительно нужно для проверки изменений backend, контрактов, конфигурации проекта или связанного C#-кода.

## CLEAR.bat

Для запуска `CLEAR.bat` из браузера можно использовать обычные ссылки вида `clearbat://iiko@host:port@login:password` и формат V2.

Справочник аргументов:
- официальный список типов и форматов запуска: `https://clearbat.iiko.online/ru/other/arguments`;
- эту ссылку стоит сохранять рядом с логикой генерации `clearbat`-ссылок как опорный источник по форматам.

Поддерживаемые типы подключения по справочнику:
- `iiko` — формат `iiko@ip:port@login:password`;
- `rdp` — формат `rdp@ip:port@login:password`;
- `anydesk` — формат `anydesk@login:password`;
- `teamviewer` — формат `teamviewer@login:password`;
- `customconnection` — кастомный тип подключения;
- `supremo` — тип подключения Supremo;
- `rustdesk` — тип подключения RustDesk;
- `rudesktop` — тип подключения RuDesktop;
- `ammyy` — тип подключения Ammyy;
- `litemanager` — формат `litemanager@login:password`;
- `assistant` — формат `assistant@login:password`;
- `aspia` — формат `aspia@ip@login:password`;
- `radmin` — тип подключения Radmin.

Правило по обязательности `password`:
- `password` обязателен только для типов `rdp`, `teamviewer`, `anydesk`, `litemanager`;
- для остальных типов подключений можно пробовать запуск без пароля, если это допускает конкретный сценарий и формат ссылки.

Кратко по аргументам V2 (`6.6.1.23+`):
- формат V2: `clearbat:/?type=iiko?url=test.iiko.it:443?login=admin?password=1234567890?encode=full`;
- `?encode=...` всегда ставится в самом конце ссылки, иначе обработка пойдет по обычному сценарию;
- `encode=full` кодирует всю V2-строку целиком;
- `encode=browser` полезен, когда браузер экранирует спецсимволы в ссылке и их нужно восстановить перед запуском утилиты;
- `encode=password` кодирует только пароль в `base64`, если не хочется кодировать всю ссылку;
- `encode` работает и для обычных ссылок, например `clearbat://iiko@host:port@login:password?encode=full`.

Для сайта это означает:
- если ссылка собирается на клиенте и может содержать спецсимволы, безопаснее ориентироваться на V2-формат;
- если проблема только в пароле, обычно достаточно `encode=password`;
- если нужно передать всю ссылку без влияния браузерного парсинга, лучше использовать `encode=full`.
