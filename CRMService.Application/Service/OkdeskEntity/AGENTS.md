# AGENTS

Директория содержит сервисы локальной работы с сущностями Okdesk и связанными справочниками.

Основные сущности:
- заявки, статусы, приоритеты, типы и группы типов;
- оборудование, параметры оборудования, типы, производители и модели;
- клиенты, категории клиентов и объекты обслуживания;
- сотрудники, группы, роли и связи сотрудников с группами;
- списания времени.

Основные сценарии:
- получение списков и карточек для UI;
- загрузка данных из Okdesk API;
- загрузка данных из облачной базы Okdesk;
- создание или обновление локальных копий сущностей;
- сверка текущих локальных заявок с Okdesk и пометка исчезнувших после удаления или объединения;
- подготовка lookup-списков для фильтров страниц.

Связанная логика:
- списки заявок и оборудования находятся в `CRMService.Web/Pages/Issues` и `CRMService.Web/Pages/Equipments`;
- API-контроллеры справочников находятся в `CRMService.Web/Controllers/OkdeskEntity`;
- доменные модели находятся в `CRMService.Domain/Models/OkdeskEntity`;
- маппинги DTO находятся в `CRMService.Application/Common/Mapping/OkdeskEntity`.
- локальные изменения разделены между `ICompanyDirectoryUnitOfWork`, `IEquipmentUnitOfWork` и `IIssuesUnitOfWork`;
- облачный OkdeskContext доступен через read-only `IOkdeskCompanyDirectorySource`, `IOkdeskEquipmentSource` и `IOkdeskIssuesSource` без формального transaction scope.

Правила изменений:
- обновления должны быть идемпотентными и не создавать дубли при повторном запуске;
- для заявок вебхуки являются источником актуальной ответственной группы; REST-список не должен очищать локальный `GroupId` или уменьшать `EmployeesUpdatedAt`, а SQL-снимок может обновлять заявку только при `incoming.EmployeesUpdatedAt >= existing.EmployeesUpdatedAt`;
- для списаний времени обычный API и вебхуки являются источником актуальных изменяемых полей; SQL API может заполнять отсутствующие SQL-специфичные поля, например `CreatedAt`, но не должен перезаписывать уже заполненные значения или актуальные поля более старым снимком;
- локальный параметр оборудования имеет собственный `Id`, уникальный `Code` и nullable `OkdeskId`: REST API и webhook сопоставляются по `Code`, SQL API и таблица связей — по `OkdeskId`;
- новые локальные `KindsParameter.Id` выдаются отрицательной SQL-последовательностью, чтобы не пересекаться с положительными историческими ID, ранее скопированными из SQL API;
- REST-схему параметров оборудования не десериализовывать в `KindsParameter`, потому что REST API не возвращает идентификатор SQL API;
- синхронизация связей сотрудников с группами должна сверять полный состав каждой полученной группы и удалять отсутствующие в нем локальные связи, в том числе когда группа стала пустой;
- курсорную пагинацию Okdesk и пагинацию по номеру страницы не смешивать; сетевые и HTTP-ошибки загрузки должны прерывать синхронизацию, а не имитировать пустой ответ;
- отсутствие заявки сначала проверять пакетным запросом по `ids[]`, затем подтверждать отдельным ответом Okdesk с полем `errors`; сетевой сбой или неожиданный ответ не должны помечать заявку удаленной;
- для зависимых сущностей сначала разрешать ссылки через локальные справочники или resolver-сервисы;
- при изменении списка полей, которые видит пользователь, обновлять соответствующий локальный `AGENTS.md` страницы.
