# План реализации страницы списка заявок

## 1. Подготовка backend-контрактов

1. Проанализировать текущую модель `Issue` и определить, каких данных уже достаточно для списка, а какие поля нужно дополнительно подтягивать через связи.
2. Спроектировать DTO для строки таблицы заявок:
   - id;
   - тема;
   - клиент;
   - ответственный;
   - дата регистрации;
   - дата решения;
   - статус.
3. Спроектировать DTO для фильтров страницы:
   - id;
   - список ответственных;
   - список авторов;
   - список типов;
   - список статусов;
   - список клиентов;
   - список ответственных групп;
   - диапазон даты регистрации;
   - диапазон даты решения;
   - номер страницы;
   - размер страницы `20 | 50 | 100`.
4. Спроектировать DTO ответа страницы:
   - список заявок текущей страницы;
   - количество элементов на странице;
   - текущая страница;
   - общее количество страниц;
   - признак, что общее количество усечено до `1000+`;
   - отображаемое количество для быстрого режима;
   - точное количество для режима по клику.

## 2. Логика выборки и фильтрации заявок

1. Добавить в application-слой метод получения списка заявок с фильтрацией и пагинацией на основе данных из БД.
2. Реализовать fail-fast-валидацию входных параметров:
   - недопустимый размер страницы;
   - отрицательная или нулевая страница;
   - некорректные диапазоны дат.
3. Реализовать фильтрацию по всем согласованным полям:
   - `id`;
   - ответственный;
   - автор;
   - тип;
   - статус;
   - клиент;
   - ответственная группа;
   - дата регистрации;
   - дата решения.
4. Реализовать два режима подсчёта:
   - быстрый подсчёт для пагинации с верхней границей `1000+`;
   - точный подсчёт по отдельному запросу при клике на количество.
5. Учесть множественные фильтры через коллекции идентификаторов.
6. Определить единый порядок сортировки списка по умолчанию, чтобы пагинация была стабильной между запросами.

## 3. Хендлеры Razor Page

1. Создать новую Razor Page для списка заявок с PageModel только для администраторов.
2. Добавить GET-хендлеры для загрузки справочников фильтров:
   - ответственные;
   - авторы;
   - типы;
   - статусы;
   - клиенты;
   - ответственные группы.
3. Добавить GET- или POST-хендлер загрузки списка заявок по текущим фильтрам.
4. Добавить отдельный хендлер точного подсчёта количества заявок.
5. Выстроить JSON-контракты в стиле проекта:
   - успешные GET возвращают DTO без лишней обёртки;
   - ошибки возвращаются через HTTP-статус и стандартный JSON с `message`.

## 4. Верстка страницы

1. Создать страницу по визуальной структуре, близкой к `Users.cshtml`:
   - контейнер страницы;
   - блок ошибок и служебных сообщений;
   - белая карточка с фильтрами;
   - белая карточка с таблицей.
2. Верхнюю панель фильтров сделать по паттерну `Report.cshtml`:
   - фильтры находятся сверху;
   - панель сворачивается и разворачивается кнопкой;
   - состояние панели должно быть визуально очевидным.
3. В фильтрах предусмотреть:
   - поле `id`;
   - множественные селекты/дропдауны для справочников;
   - два диапазона дат;
   - селектор размера страницы `20 / 50 / 100`;
   - кнопку сброса фильтров, если она потребуется по выбранной UX-схеме.
4. Под фильтрами разместить таблицу заявок с колонками:
   - № заявки;
   - тема;
   - клиент;
   - ответственный;
   - дата регистрации;
   - дата решения;
   - статус.
5. В строках таблицы не реализовывать переход внутрь заявки.

## 5. Frontend-логика страницы

1. Создать отдельный JS-файл страницы в стиле существующих страниц проекта.
2. Реализовать инициализацию через `DOMContentLoaded` и `init`-функцию.
3. Загрузить справочники фильтров и стартовую страницу данных при первом открытии.
4. Реализовать автоматическое обновление списка при любом изменении фильтра.
5. Для частых изменений фильтров предусмотреть защиту от лишних гонок запросов.
6. Реализовать отображение пустого состояния таблицы.
7. Реализовать отображение ошибок загрузки без перезагрузки страницы.

## 6. Пагинация

1. Реализовать нижний блок пагинации с поведением по макету:
   - при первой загрузке пользователь находится на странице `1`;
   - сначала отображаются страницы `1..5`;
   - при переходе дальше появляются кнопки `<<`, `<`, `>`, `>>`;
   - `<<` ведёт на первую страницу;
   - `<` ведёт на предыдущую страницу;
   - `>` ведёт на следующую страницу;
   - `>>` ведёт на последнюю страницу.
2. Реализовать вычисление набора отображаемых номеров страниц без перезагрузки.
3. Реализовать обновление списка при переключении страниц.
4. Реализовать сброс на первую страницу при любом изменении фильтра или размера страницы.
5. Реализовать текст общего количества:
   - в быстром режиме показывать `1000+`, если элементов больше тысячи;
   - по клику отправлять отдельный запрос на точное количество;
   - после точного ответа обновлять отображение без повторной загрузки страницы.

## 7. Интеграция в навигацию

1. Добавить ссылку на новую страницу в боковое меню для пользователей с ролью `ADMIN`.
2. Сохранить существующую логику подсветки активного пункта меню.
3. При необходимости подготовить иконку или использовать уже существующую, не ломая текущую структуру layout.

## 8. Проверка и стабилизация

1. Проверить сценарий первой загрузки страницы.
2. Проверить работу каждого фильтра отдельно и в комбинации.
3. Проверить поведение множественных фильтров.
4. Проверить работу пагинации на наборах:
   - меньше 5 страниц;
   - больше 5 страниц;
   - больше 1000 заявок.
5. Проверить клик по `1000+` и обновление на точное значение.
6. Проверить переключение размера страницы `20 / 50 / 100`.
7. Выполнить `dotnet build` после реализации и исправить все ошибки сборки.

## 9. Риски, которые нужно учесть при реализации

1. У `Issue` сейчас есть только числовые ссылки на связанные сущности, поэтому для таблицы и фильтров может понадобиться явная загрузка связанных данных или отдельная проекция на запросе.
2. Для фильтра по автору нужно заранее проверить, что в основной БД авторы заявок представлены консистентно и доступны для выборки так же, как ответственные.
3. Для производительности важно не делать точный `COUNT(*)` на каждое изменение фильтра, а вызывать его только по явному клику на `1000+`.
4. При смене фильтров и страниц нужно исключить рассинхронизацию между текущим состоянием UI и ответами от более старых запросов.
