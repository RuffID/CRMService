# Этап 4. Тесты Application

Status: Not Started

## Подход

Application.Tests — быстрые unit-тесты. Репозитории, `IUnitOfWork`, `IOkdeskUnitOfWork`, внешние API, notifications, Options и logger заменяются контролируемыми doubles. EF Core provider и Docker здесь не используются.

До массового покрытия application services выполнить [этап декомпозиции Unit of Work](02-unit-of-work-decomposition.md). Тесты должны подменять минимальный сценарный Unit of Work, а не закреплять старую связанность гигантской общей fixture. Если часть тестов создаётся параллельно с миграцией, для каждого сервиса настраивать только реально используемые зависимости и не создавать reusable fake старого god object.

## Приоритет 1: детерминированная прикладная логика

- `Hasher`: успешная проверка, неверный пароль, разные salts, повреждённый формат hash и пустой ввод согласно принятому контракту;
- `GenerateRandomString`: длина, допустимый набор символов, граничные значения и достаточная вариативность без статистически нестабильных assertions;
- `EntitySyncService`: последовательное выполнение для одного `(type,id)`, параллельность разных ключей, освобождение блокировки после исключения, cancellation ожидания;
- mapping-классы Authorization/Okdesk: перенос обязательных полей, null-сценарии и отсутствие потери идентификаторов;
- report services: передача диапазона/фильтров в соответствующий repository и корректная упаковка результата.

Если тест выявляет существующую ошибку, сначала оформить её как отдельный defect. Не записывать очевидно ошибочное поведение как желаемый контракт только ради зелёного теста.

## Приоритет 2: сценарии сервисов

- Authorization: создание/обновление пользователя, роли, блокировки, duplicate/not-found и сохранение через UoW;
- PlanSettings: загрузка и согласованное сохранение планов, норм и цветовых правил;
- Okdesk services: локальная выборка, API/cloud sync, идемпотентность, cancellation и правила лимитов;
- resolvers: local hit, sync-and-retry, отсутствие зависимой сущности и проброс первопричины;
- webhooks: `CanHandle`, маршрутизация события, повторная доставка и вызов notification только в нужных случаях;
- `UpdateDirectoriesService`: фиксированный порядок зависимых обновлений и остановка на первичной ошибке.

## Тестовые данные

Создать небольшие builders по предметным областям (`UserBuilder`, `IssueBuilder`, `EquipmentBuilder`). Builder должен создавать минимально валидный объект и позволять переопределить только значимые для сценария поля. Не использовать одну глобальную mutable модель между тестами.

## Критерии завершения

- Ни один тест Application не вызывает сеть, EF Core database provider или файловую систему.
- Для каждого крупного сервиса есть happy path, ожидаемая ошибка и cancellation/exception path, если он поддерживается.
- Проверяются как возвращаемые данные, так и границы: вызовы repository, `SaveChangesAsync`, transaction и внешних сервисов.
